Miro.Design

Overview

Miro.Design is the internal platform where the design system is published twice from one source: as pages a designer reads, and as data a coding agent fetches. I set the model it runs on — a quality bar that changes volume instead of standing still, and four areas that each replaced something that used to be word of mouth.

The platform

Five questions, and one of the readers is not a person.

It opens on the questions a designer actually arrives with rather than a table of contents. Seven of its eight readers are people; the eighth is the coding agent working on their behalf, and it needs the same answers in a form it can fetch.

Every frame below carries the same switch. Flip one and they all change register at once.

Long story, short.

Designers ship through agents now, and the system was invisible to them.

A design system that lives as guidance — prose, principles, a library — is something a person opens and applies judgement to. A coding agent does neither. It is fast, literal and confident, and it will build the screen whether or not it knows the rules: hand-rolled chrome where a component existed, invented colour, nothing that survives translation.

Nobody finds out until handover, which is the most expensive possible moment to find out.

The gate that was already tried

Two hard gates had been built before, and both were shelved.

The obvious fix is enforcement: define the rules, block anything that breaks them. Miro had tried it twice. The lesson recorded from those attempts was blunt — forcing token-only usage backfires, because people hack around the design system instead of using it.

Which means the problem was never the rules. It was applying all of them at every moment, including the moments where the work is still an idea. What follows is the platform in four parts, and what each part replaced.

What the design system contains

Values resolved once, with the gaps named.

The product language is the four surfaces and the layers underneath them: colour, the one physical scale, type, content and motion. Colour is the clearest case. Nine hues, each carrying a family of seven semantic roles, so you pick a hue and the roles come with it rather than picking a value and hoping.

Every resolved role carries its measured contrast. The roles nobody has settled say so.

The run, start to finish

The quality conversation moved off the end of the project.

One feature, from a screenshot to a pull request. What makes it a run rather than a workflow diagram is that two of the steps are decisions you make out loud: promote this, or kill it.

One checklist, three volumes

So the bar became a variable.

This is the mechanism under the run. The checklist never changes; what changes is the consequence of breaking one of its rows, what the agent reaches for first, and what you are left holding. Switch volumes and watch the rows refuse to move.

What you can pull in

Four kinds of thing, and knowing which is which is most of the battle.

The toolkit is where a designer sets themselves up. Its real work is definitional: people were mixing up things the agent reads with things the product is built from, which is how you end up with a prototype that behaves correctly and ships nothing, or ships everything and behaves like a stranger.

What everyone is building

The system finally gets to see itself being used.

The prototypes page lists every app on the platform, resolved to a person, a team, a status and the thing it was cloned from. It sounds like an activity feed. It is actually the evidence base: what people reached for, and what they had to hand-roll because nothing existed.

Neither move works alone

The graded bar and the second reader are one idea.

A bar that changes volume is useless if the thing building the screen cannot find out what correct means at each volume — it just becomes a slower way to be wrong. And a machine-readable design system is pointless if all it can say is no, because that is the gate that already failed twice.

Put together they work: the agent can read what the rule is, and read how loudly it applies right now.

Publishing the uncertainty

A graded bar is only honest if you publish which grades are real.

Four labels run across everything, and the fourth is the load-bearing one: a gap with no owner, a proposal nobody ratified, a value the system has no answer for. If a thing carries no status, nobody has decided — which is unresolved, not stable.

Which is why the three volumes carry that label themselves. The mechanism that grades everything else is published as a proposal, on the same page that lists everything the platform does not yet know. That is not a caveat. It is the only thing that makes the rest of it trustworthy.

Shipped outcome

Internal, in use, and still arguing with itself in public.

  1. A designer names the volume and gets the matching severity, instead of negotiating with a bar that never moved.
  2. The language is published once and read two ways, so the value a designer checks by eye is the value an agent fetches.
  3. Roles nobody has resolved say so, rather than being filled in with a plausible guess that then ships.
  4. Setup is a dated manifest instead of folklore, and the four kinds of thing in it are finally distinguishable.
  5. What the system could not cover comes back as evidence, so the language is revised from what happened rather than from what was intended.

About

A design system used to be something you read. Most of the reading is now done by something that acts on it immediately and never asks a follow-up question. That changes what the documentation is for: less persuasion, and much more precision about what is true, what is proposed, and what nobody has decided yet.
